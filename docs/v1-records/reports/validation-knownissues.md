# HourKeep — Known-Issues Validation & Latent Code-Health Audit

READ-ONLY investigation. Scope: verify the four carried-forward known issues in
`.agents/reports/w8a-status-report.md` §5 against the code (Part A), and surface undocumented
issues the report does not mention (Part B).

Repo state at audit: `HEAD = 1307625` on `main` (matches the report's deployed commit).
`npm audit` run live against the installed tree. Every item below is **a lead to verify**, not a
settled defect — citations are given so each can be re-checked against the primary source.

---

## Summary answer first

**Part A — the four §5 known issues:**

1. **Offline path unautomated — CONFIRMED.** No e2e spec drives the app with the network off. Nothing
   calls `context.setOffline` / `page.route` abort / `setOffline`. The only service-worker touch is a
   capability probe (`"serviceWorker" in navigator`). The offline-first core is untested end-to-end.
2. **~10 React Compiler errors suppressed by a pin — PARTIALLY CONFIRMED, count overstated.** The pin
   exists (`overrides.eslint-plugin-react-hooks: "7.0.1"`). But only **two** inline
   `react-hooks/set-state-in-effect` disables exist (`OfflineIndicator.tsx`, `app/page.tsx`), plus two
   `exhaustive-deps` disables (`IncomeDashboard.tsx`, `DocumentViewer.tsx`). Three of the five components
   the brief names (`ActivityForm`, `IncomeEntryForm`, `StorageInfo`) carry **no** such suppression. The
   "~10 errors" figure is not visible as inline disables; if real, they are suppressed by the version pin
   itself, not by in-file comments. **Recommend the report say "pin-suppressed, not individually
   annotated — exact count unverified" rather than "~10."**
3. **`next` advisories — CORRECT THE REPORT.** Installed `next@16.0.1` (exact). The report's "8 high, 1
   critical" is **wrong for the whole tree and even for `next` alone.** Live `npm audit`:
   **23 total — 1 critical, 18 high, 4 moderate.** Top advisory: **GHSA-9qr9-h5gf-34mp**, "RCE in React
   flight protocol," **critical, CVSS 10.0**, affecting `next >=16.0.0-canary.0 <16.0.7`. The
   static-export mitigation **holds**: `output: "export"`, no `middleware.ts`, no `"use server"`, no
   `route.ts` handlers, no `app/api` — so the server-side RCE/DoS vectors are not reachable in the
   deployed artifact. But the count and severity in the report are understated.
4. **Node floor — CONFIRMED.** `engines.node: ">=22.22.2"`; **no `.npmrc`**, so `engine-strict` is off
   and the floor is advisory only locally. CI pins `node-version: "22.23.2"` in `deploy.yml`.

**Part B — most material undocumented finding:** the **exclusion-screening persistence path is dead in
the running app.** `saveScreening`/`archiveScreening` (the only writers of `db.exemptions`) have **zero
production callers**; `/exemptions` is a redirect stub to `/how-to-hourkeep`, which writes
`db.assessmentResults` instead. Consequently the Settings "Exemption Screening" / "Screening History"
sections (which read `getLatestScreening`/`getScreeningHistory`) can **only ever show the empty state**,
and the export package's `exclusionScreenings` is always empty. This is broader than the report's §2/§3
note (which only flags "no exclusion-*document* writer, no capture UI").

## Part A — evidence

### A1. Service-worker / offline path is unautomated — CONFIRMED

- `e2e/` contains 6 specs: `browser-capabilities`, `console-clean`, `delete-all-mobile`,
  `evidence-package`, `month-scoping`, `pwa-assets`.
- Grep for `offline|setOffline|context.setOffline|navigator.onLine|serviceWorker` across
  `e2e/*.spec.ts`: the only hits are `"serviceWorker" in navigator` as a **capability assertion**
  (`browser-capabilities.spec.ts:230`) and `waitUntil: "networkidle"` navigations (which require the
  network to be *up*, the opposite of an offline test). No spec toggles the network off, aborts routes,
  or asserts the app works from the service-worker cache.
- `next.config.ts` wraps the config in `withPWA({ register: true, skipWaiting: true, disable: NODE_ENV
  === "development" })`. The SW is generated by `next-pwa` and is **disabled in dev**, so `npm run dev`
  never exercises it either — the only place it runs is the production export, which no automated test
  loads offline.
- `pwa-assets.spec.ts` checks the manifest/icons (the regression it was written for) but not offline
  behavior.

Lead to verify: a Playwright spec using `context.setOffline(true)` after first load, asserting a tracked
route still renders. Nothing like it exists today.

### A2. React Compiler suppressions — pin confirmed, inline count overstated

- `package.json` → `"overrides": { "eslint-plugin-react-hooks": "7.0.1" }`. Confirmed.
- Inline `react-hooks/set-state-in-effect` disables (exactly two):
  - `src/components/OfflineIndicator.tsx:13` and `:21`
  - `src/app/page.tsx:13`
- Inline `react-hooks/exhaustive-deps` disables (two):
  - `src/components/income/IncomeDashboard.tsx:92`
  - `src/components/documents/DocumentViewer.tsx:103`
- The brief's named set also includes `ActivityForm`, `IncomeEntryForm`, `StorageInfo` — **none of these
  carry a `react-hooks/*` suppression.** Their only `eslint-disable` usages elsewhere are
  `@next/next/no-img-element` and `@typescript-eslint/no-unused-vars`, which are unrelated.
- Conclusion: the "~10 errors" are not individually annotated in-file. If they exist they are latent
  violations that `eslint-plugin-react-hooks@7.0.1` does not report but a `7.1.x` would. The report
  should either produce the count by running the newer linter or soften the claim.

Lead to verify: temporarily bump `eslint-plugin-react-hooks` to `7.1.x` in a scratch install and run
`npm run lint` to get the true count. Not done here (read-only; would mutate the tree).

### A3. `next` version and audit — CORRECT THE REPORT

- `package.json` → `"next": "16.0.1"` (exact, no caret). `eslint-config-next: "16.0.1"` matches.
- Live `npm audit --json` metadata: `{ critical: 1, high: 18, moderate: 4, total: 23 }`. The report's
  "8 high, 1 critical" does not match the tree.
- `next` itself is rated **critical** via GHSA-9qr9-h5gf-34mp (RCE in React flight protocol, CVSS 10.0,
  range `>=16.0.0-canary.0 <16.0.7`), plus moderate (Server Actions source exposure, GHSA-w37m-7fhw-fmv9)
  and high (DoS via Server Components, GHSA-mwv6-3258-q52c) advisories — all server-feature vectors.
- Much of the `high` count is dev-only transitive noise: `brace-expansion` ReDoS (several GHSA ids under
  `@typescript-eslint`/glob tooling), `eslint-config-next`/`fast-glob`, `@vitest/*` path-traversal
  (GHSA-82fw-gwwq-j7x9, moderate). These do not ship to users.
- **Static-export mitigation confirmed:** `next.config.ts` sets `output: "export"`; no `middleware.ts`
  anywhere; grep for `"use server"` → 0 matches; no `route.ts`/`route.tsx` under `src/app`; no `app/api`
  directory. So the RCE/Server-Actions/Server-Components vectors are not present in the deployed artifact.
  The exposure characterization in the report is right; the **numbers** are wrong.

Recommended corrected line for §5: "next@16.0.1 — audit reports 23 advisories (1 critical, 18 high,
4 moderate); the critical (GHSA-9qr9-h5gf-34mp, CVSS 10) and the high/DoS ones are server-feature
vectors not reachable under `output: 'export'` with no middleware/server-actions/route-handlers; most
'high' entries are dev-only transitive. Patch path: `next >=16.0.7` clears the critical. Deferred to W1."

### A4. Node floor — CONFIRMED

- `package.json` → `"engines": { "node": ">=22.22.2" }`.
- No `.npmrc` in the repo root, so `engine-strict` is unset → the engines floor is a warning, not a hard
  gate, on local installs (`EBADENGINE` does not fail `npm ci`). This matches the CHANGELOG reasoning in
  `deploy.yml`.
- CI pins `node-version: "22.23.2"` exactly in `.github/workflows/deploy.yml`. Confirmed.

## Part B — undocumented findings (severity-ranked; each a lead to verify)

### B1. HIGH — Exclusion-screening persistence is dead; Settings screening sections can only show empty

- `src/lib/storage/exemptions.ts` exports `saveScreening` (the sole writer of `db.exemptions`) and
  `archiveScreening`. **Neither has any caller in `src/app/**` or `src/components/**`** — grep across all
  of `src` finds only the definitions and tests.
- `src/app/exemptions/page.tsx` is a **redirect stub**: it renders a spinner and
  `router.push("/how-to-hourkeep")`. The standalone screening was replaced by the "How to HourKeep"
  assessment, which persists to `db.assessmentResults` / `db.assessmentHistory`, **not** `db.exemptions`.
- `src/app/settings/page.tsx` reads `getLatestScreening`/`getScreeningHistory` (`db.exemptions` /
  `db.exemptionHistory`) to render the "Exemption Screening" and "Screening History" panels, and its
  "Start Screening" / "View Results" / "Re-screen" buttons all `router.push("/exemptions")`. Because
  nothing ever writes `db.exemptions`, those panels are permanently stuck on the empty state and the
  buttons loop the user through a spinner into the assessment.
- `src/app/export/package/page.tsx` reads `db.exemptions.toArray()` as `exclusionScreenings` — always
  empty for the same reason.
- Impact: user-visible dead-end in Settings; an export section that can never populate; three storage
  functions and their cascade/archive logic that run only in tests. The report's §2/§3 only says "no
  exclusion-*document* writer and NO capture UI (gap 8.5 PARTIAL)" — the dead *screening* writer and the
  always-empty Settings UI are not called out.
- Lead to verify: load the built app, open `/settings`, confirm the screening section shows the empty
  "Start Screening" copy regardless of having completed the assessment; confirm `db.exemptions` stays
  empty after an assessment run (DevTools → IndexedDB).

### B2. MEDIUM — Income-document orphaned blobs are unreclaimable by any automatic path

- `src/lib/storage/incomeDocuments.ts:48-51` (comment) and `income.ts:50-53` both state there is **no
  income counterpart to `cleanupOrphanedDocuments`**. The activity-side sweep
  (`activities.ts:cleanupOrphanedDocuments`) scans `db.documents` vs `db.activities` only; it never
  touches `db.incomeDocuments` / `db.incomeDocumentBlobs`.
- The only invocation of `cleanupOrphanedDocuments` in app code is a **manual button** in
  `src/components/settings/StorageInfo.tsx:102` (`handleCleanupOrphaned`) — there is no scheduled or
  automatic reclaim, and it does not cover income docs.
- The cascade delete `deleteIncomeEntryWithDocuments` is correct and transactional-in-spirit, so orphans
  only arise on a *partial failure* mid-cascade or a future bare-row delete — but if they do arise,
  nothing ever reclaims them, and blobs are the largest rows. This is the same class as the known
  `deleteDocument` non-atomic note but on a table with **no janitor at all**.
- Lead to verify: induce a mid-cascade failure (mock `deleteIncomeDocument` to reject) and confirm the
  orphaned `incomeDocumentBlobs` row persists with no reclaim path. (Characterization tests already pin
  the "nothing reclaims these" behavior: `documentWritesAreAtomic.test.ts`,
  `deleteIncomeEntryWithDocuments.test.ts`.)

### B3. MEDIUM — Components reach into Dexie directly, violating the storage-layer boundary

- Both `component-standards.md` and `data-migration-standards.md` state "components never touch Dexie;
  reads/writes go through `src/lib/storage/`."
- Violations found:
  - `src/components/settings/StorageInfo.tsx:19` → `import { db } from "@/lib/db"` and reads tables
    directly for the storage breakdown.
  - `src/app/export/package/page.tsx:116-117` → `db.documents.toArray()`, `db.incomeDocuments.toArray()`,
    `db.exemptions.toArray()` directly in the page.
- Impact: these are the exact readers that a schema change must find and update by hand (the migration
  standard's "grep for the field name, not just the type"). Direct Dexie access in the UI widens that
  surface. Low user impact today, real maintenance/data-correctness risk at the v6→v7 bump W3 owns.
- Lead to verify: grep `from "@/lib/db"` under `src/app` and `src/components` for the full list before W3.

### B4. LOW/INFO — Stored verdict-typed fields persist a determination the app may not make

- `src/types/income.ts:71` `MonthlyIncomeSummary.isCompliant: boolean` and
  `src/types/index.ts:162` `MonthlySummary.isCompliant: boolean`. Both are explicitly annotated "NAME IS
  A VERDICT — renamed in W7b (ADR-0003)." `income.ts:getMonthlyIncomeSummary` actively computes and
  returns `isCompliant: effectiveIncome >= threshold`.
- This is a *known/deferred* item (W7b owns the rename) but is a live ADR-0003 boundary smell worth
  keeping on the list because the field is computed and returned today, not merely declared.

### B5. LOW — Theme sets no touch-target minimum; 44×44 is enforced per-call-site instead

- `component-standards.md` is explicit: the fix for the 44×44 target is `MuiButton`/`MuiIconButton`
  theme overrides, **not** `sx={{ minHeight: 44 }}` repeated at every call site.
- `src/theme/theme.ts` `MuiButton.styleOverrides.root` sets only `borderRadius` and `padding`; there is
  **no `MuiIconButton` override and no min-size**. Compliance is achieved by scattered
  `sx={{ minWidth: 44, minHeight: 44 }}` across ~10 components (Calendar, MonthNavigator,
  ReviewPeriodPanel, HelpTooltip, DashboardGuidance, settings, etc.). Any new button that forgets the
  `sx` silently falls back below 44px.
- aria-labels, by contrast, are in good shape — spot-checked `ActivityList`, `ActivityForm`,
  `DocumentViewer` zoom controls, `tracking/page.tsx` header icons, `IncomeEntryList`: every icon-only
  control carries an `aria-label`. No egregious a11y gap found beyond the theme-level target.
- W10 owns a11y, so this is "note, don't fix," but the systemic shape (no theme floor) is worth recording
  so W10 fixes the root rather than more call sites.

### B6. LOW — Global-window method coupling in the tracking header

- `src/app/tracking/page.tsx:698-726`: the "show help" IconButton calls
  `window.showDashboardGuidance?.()` and, if absent, clears localStorage/sessionStorage keys and does a
  full `window.location.reload()`. Relying on a method bolted onto `window` (set elsewhere by
  `DashboardGuidance`) is fragile — a mount-order change silently drops into the reload fallback. Not a
  current user-facing break, but brittle. Lead: confirm `DashboardGuidance` always mounts before the
  header can be clicked.

### B7. INFO — TODO/FIXME/HACK/XXX scan is clean

- Grep of `TODO|FIXME|HACK|XXX` across `src/**/*.{ts,tsx}` returns **no genuine action markers in
  production code**. The only hits are the word "TODO" inside test *guard* comments
  (`policy.test.ts:235`, `no-verdict.source.test.ts:127`) and "XXX" in a phone-format mask comment
  (`validation/profile.ts:22`). This is a positive finding — the codebase does not carry a backlog of
  inline debt markers — and is itself undocumented in the report.

### B8. INFO — Policy-literal discipline (ADR-0001) is holding

- Grep for `80|580|7.25|4.33` outside `src/lib/policy/` in non-test code returns **only** matches inside
  comments/doc-strings or in `federalDefault.ts` (marked `// policy-literal-ok`), or values passed in as
  parameters (`buildTextReport.ts` takes `thresholds`; `calculations.ts`, `education.ts` read from the
  profile). No bare hardcoded policy value was found in executable non-test code outside the policy
  module. ADR-0001 is being respected. (Report does not claim otherwise; recorded as corroboration.)

### B9. INFO — Latent date-bound construction in income month queries (already characterized)

- `income.ts:getIncomeEntriesByMonth` and `getIncomeEntriesForLast6Months` use string bounds
  `` `${month}-01` `` .. `` `${month}-31` ``. This is **not a bug today** — it is a lexical string
  comparison that is safe for short months (`"2026-02-31"` sorts after `"2026-02-28"`), and
  `income.characterization.test.ts:196,217` pins exactly this behavior. Flagged only because W5's
  month-scoping or any switch to `Date` objects would turn `"2026-02-31"` into an invalid date; the
  characterization test already warns of this. No action now.

## Conclusions

- **Part A:** issues 1 and 4 are confirmed as stated. Issue 2 is real (the pin exists) but the report's
  "~10 errors" is not substantiated by in-file suppressions and should be re-counted or softened. Issue 3
  needs a numeric correction — the tree has **23** advisories (1 critical / 18 high / 4 moderate), the
  headline `next` advisory is a **CVSS-10 critical** (GHSA-9qr9-h5gf-34mp), and the static-export
  mitigation genuinely holds (verified: no middleware, no server actions, no route handlers, no api).
- **Part B:** the standout is **B1** — the exclusion-screening write path is dead and the Settings
  screening UI is a permanent empty-state dead-end, which is a user-reachable broken flow broader than
  the report's gap-8.5 note. **B2/B3** are data-integrity/boundary risks that matter most at the W3 v7
  migration. **B5** is a real-but-W10-owned systemic a11y root cause. The remainder (B4, B6) are smells;
  B7/B8/B9 are positive/benign corroborations.

## Recommendations (implement nothing here)

1. **Fix §5 of the report**: correct the audit numbers (23 / 1-crit-18-high-4-mod, GHSA-9qr9-h5gf-34mp)
   and soften the "~10 React Compiler errors" to "pin-suppressed, exact count unverified."
2. **Add B1 to the gap list** as a user-visible broken flow, not just a PARTIAL: either wire the
   assessment to persist an exclusion-screening projection into `db.exemptions`, or remove/relabel the
   Settings screening sections and `/exemptions` buttons so they don't dead-end. (Likely W4's exclusion
   capture, but the *dead settings UI* is shippable breakage now.)
3. **Before the W3 v7 bump**, route B3's direct `db.*` reads in `StorageInfo.tsx` and
   `export/package/page.tsx` through `src/lib/storage/`, and add an income-document orphan sweep (B2) or
   explicitly document that income orphans are unreclaimable.
4. **W1**: bump `next` to ≥16.0.7 to clear the critical; re-run `npm audit` and reconcile the count into
   the report.
5. **W10**: add `MuiButton`/`MuiIconButton` theme min-size overrides (B5) rather than more per-call-site
   `sx`.
